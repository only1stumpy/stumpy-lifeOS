# Техническая основа LifeOS

Документ описывает устройство системы. Что проверено на реальных сервисах и что нет, записано в [status.md](status.md); развёртывание — в [deployment.md](deployment.md), эксплуатация — в [operations.md](operations.md), переменные окружения — в [configuration.md](configuration.md).

## Принятый стек и состояние

| Область | Реализация в репозитории | Состояние интеграции |
|---|---|---|
| Приложение | Next.js App Router, React, TypeScript | Vercel, регион `fra1` (`vercel.json`) |
| Telegram | grammY, webhook и Mini App `initData` | Webhook `/api/telegram` с секретным заголовком |

| SQL-доступ | Drizzle ORM и Drizzle Kit | Схема `src/db/schema.ts`, миграции в `drizzle/` |
| Проверка ввода | Zod | Используется для команд Mini App и ответов ИИ |
| ИИ | Карточки Gemini, Groq, OpenRouter, Cloudflare Workers AI и custom OpenAI-compatible (Cerebras в каталоге заблокирован); стандартные карточки показывают официальные логотипы и ссылки для получения ключа, список моделей обновляется через API. Пользователь выбирает модели, аккаунты и общий порядок fallback. API-ключи шифруются AES-256-GCM. | Gemini требует подтверждения Free Tier: API-ключ наследует биллинг проекта, который LifeOS автоматически не проверяет. Cloudflare подтверждается так же (Workers Paid включается отдельно); Account ID хранится внутри `endpoint` аккаунта, список моделей фиксированный (API списка не подтверждён), платные модели Kimi/GLM-5.x/DeepSeek-V4 не предлагаются, ответ запрашивается без `response_format` (его поддержка в OpenAI-compatible режиме Cloudflare не подтверждена) и проверяется схемой. Cerebras не участвует в fallback: пробный доступ требует платёжный метод. |
| Расписание | Защищённый маршрут сводок | cron-job.org вызывает `/api/cron` каждые 30 минут |
| Дизайн | Medeo, Liquid Glass с SVG-преломлением и CSS-fallback | См. [DESIGN.md](../DESIGN.md) |

Точные версии зависимостей задаёт `package.json`; TypeScript закреплён на `5.9.3`, `package-lock.json` фиксирует разрешённое дерево. В `next.config.ts` выставлен `experimental.useTypeScriptCli: false`, чтобы Next.js использовал TypeScript API. Требуется Node.js `>=24` (`engines` в `package.json`, CI на Node 24). Установка выполняется через `npm ci`.

В приложении нет отдельного сервера, Redis, банковской синхронизации или чужого движка. Исходные изображения еды передаются облачному ИИ во время разбора, но приложение не сохраняет их в собственной постоянной базе. Провайдер обрабатывает полученные данные по своим условиям; LifeOS не контролирует его хранение.

## Приложение и API

Интерфейс, серверные маршруты и доменная логика находятся в одном Next.js-проекте. На совместимых Telegram-клиентах Mini App после инициализации вызывает `requestFullscreen()`; при отсутствии поддержки остаётся обычное развёрнутое представление. Клиент читает `isFullscreen`, `safeAreaInset` и `contentSafeAreaInset` из Telegram WebApp API и обновляет их по событиям изменения fullscreen и safe area. В fullscreen шапка резервирует минимум 80 px сверху, а также учитывает безопасные отступы; обычное развёрнутое представление сохраняет компактную шапку.

Основные вызовы Mini App требуют заголовок `Authorization: tma <Telegram initData>`; сервер сверяет подпись и срок данных и использует проверенный Telegram ID для выбора отдельного профиля. Клиентский `initDataUnsafe` сам по себе не используется для авторизации. Для API-проверки срок `initData` по умолчанию — 24 часа. `TELEGRAM_OWNER_ID` необязателен: метрики квот Gemini для владельца и запасной Telegram ID для CLI-бэкапа; профиль данных он не определяет.

| Метод и путь | Назначение | Доступ |
|---|---|---|

| `GET /api/summary?period=day\|week\|month&start=YYYY-MM-DD` | Личный отчёт за календарный период и уже подготовленные советы из кэша, без ожидания ИИ | Telegram `initData` пользователя |
| `POST /api/summary?period=day\|week\|month&start=YYYY-MM-DD` | Советы ИИ по кнопке «Получить советы» (если не успели подготовиться вместе со сводкой); кэшированные ответы без нового вызова провайдера | Telegram `initData` пользователя |

Маршруты заданы в `src/app/api/`. Команды и их поля — в `src/domain/commands.ts`. Бот отвечает на `/start`, `/help`, `/today`, `/summary`, `/export` и `/cancel`, а также обрабатывает сообщения, фотографии и кнопки подтверждения.

## Данные и миграции

Схема `src/db/schema.ts` описывает профиль, Telegram-события, черновики, питание, финансы (счета, категории, курсы, операции, регулярные платежи, планы покупок, долги), тренировки и ИИ-профили; история изменений — SQL-файлы в `drizzle/` и [database.md](database.md). Все пользовательские строки ограничены ID профиля.

Для планов будущих покупок реализована отдельная модель, изолированная по Telegram-профилю и отделённая от записанных операций. Пока покупка не подтверждена как расход, планируемая сумма не участвует в балансе и отчётах.

Долг хранит человека, направление (`i_owe` или `owed_to_me`), первоначальную сумму в основной валюте, необязательный срок и заметку. Остаток вычисляется как первоначальная сумма минус отдельные записи возвратов. Каждая запись возврата связана с финансовой операцией; старый долг создаётся без исторического движения счёта. Явные сообщения бота создают черновик и требуют нажатия «Записать»; Mini App использует отдельные формы создания и возврата. Cron ежедневно напоминает об открытом долге начиная с даты срока, уведомление за каждый локальный день дедуплицируется ключом доставки.

Все пользовательские данные связаны с отдельным Telegram-профилем через `ownerId`, ссылающийся на `ownerSettings`. Telegram ID проверяется подписью Bot API перед каждой Mini App операцией и при обработке личного чата. Суммы хранятся в исходной валюте. Внутренний код `PRB` означает приднестровский рубль, а не российский `RUB`.

История КБЖУ для календаря строится из всех сохранённых записей питания и группируется по локальной дате владельца. Новая таблица и миграция не нужны: `nutritionDays` содержит каждую дату с едой и текущую дату, даже если в ней пока нет записей. Отчёт расходов `expenseDays` сохраняет отдельное ограничение последними 31 днями. Календарь не трактует отсутствие записей как нулевое потребление.

Валюта — код из 3–5 латинских букв (`^[A-Z]{3,5}$`, ISO или свой). Основная валюта (`owner_settings.base_currency`) задаётся валютой первого счёта и дальше не меняется; итоги, планы и долги считаются в ней. Операция в неосновной валюте хранит снимок ручного курса (`rate_to_base`, единиц основной валюты за единицу операции), действовавшего для времени этой операции; курсы лежат в `exchange_rates` по валюте и дате начала действия. При вводе курса задаётся дата начала его действия; новый курс не переоценивает уже сохранённые операции. Валютного сервиса и синхронизации остатков нет.

Финансовая операция хранит положительную сумму в minor units; знак отображения определяется типом операции: расход — минус, доход — плюс. Эта визуальная подпись не меняет формулу остатка счёта. Обзор вкладки «Финансы» сначала показывает расчётный баланс основного счёта, а расходы за день и месяц располагает ниже.

`npm run db:generate` создаёт миграцию по Drizzle-схеме; `npm run db:migrate` применяет её к `DATABASE_URL`. Состояние миграций в production: [status.md](status.md); процедура применения (до merge PR) — в [deployment.md](deployment.md).

## Сообщения, ИИ и подтверждения

Telegram webhook проверяет секрет, сохраняет update в БД и возвращает ответ Telegram; обработку продолжает Next.js `after()` внутри времени жизни функции. Ошибки и зависшие события могут быть повторены cron-маршрутом до трёх попыток. `after()` ограничен серверной функцией и не является долговечной очередью.

Каталог предоставляет компактный список Gemini, Groq, OpenRouter и расширенного OpenAI-compatible режима (плюс заблокированную карточку Cerebras). Карточки используют официальные логотипы и ссылки на страницы получения API-ключей. `/start` объясняет роль API-ключа и открывает Mini App; при первом запуске Mini App показывает мастер из трёх шагов (объяснение ключа, рекомендованный сервис с инструкцией и полем ключа, примеры сообщений), который подключает аккаунт под именем сервиса, принимает автоматически выбранные модели и очередь и сразу завершает онбординг. Описанные ниже экраны каталога, моделей и очереди — расширенные настройки. После выбора провайдера отдельный экран объясняет его условия и подключение. Ключ проверяется коротким тестовым запросом до шифрованного сохранения; после успеха открывается отдельный экран моделей, где все обнаруженные подходящие модели включены по умолчанию. Следующий отдельный экран задаёт общую очередь моделей со всех аккаунтов и провайдеров. После первичного онбординга этот набор экранов открывается повторно отдельной вкладкой с шестерёнкой в нижней навигации; заголовок LifeOS не является кнопкой. `ai_provider_model_selections.sort_order` хранит именно этот порядок; один выбранный модельный профиль разворачивается сервером в аккаунтные кандидаты, а порядок аккаунтов служит резервом при одинаковой модели. Новый профиль добавляет ранее неизвестные модели в конец очереди; при удалении профиля модели без оставшихся подключений очищаются из очереди. `owner_settings.ai_onboarding_completed` позволяет пройти онбординг один раз, а `ai_model_queue_initialized` отмечает первичное включение доступных моделей. Бесплатные модели фильтруются по правилам провайдера: актуальный allowlist Gemini/Groq и OpenRouter `:free` с нулевой ценой. Каталог OpenRouter запрашивается с `max_price=0`; результат дополнительно проверяется по суффиксу `:free` и нулевой цене ввода/вывода. У Gemini запрос списка моделей использует `x-goog-api-key`, а OpenAI-compatible запрос генерации — `Authorization: Bearer`; эти заголовки намеренно разделены. При сбое приложение пробует следующую модель и её подходящие аккаунты; для фотографии подходят только модели с заявленной поддержкой изображений. Успешные, неудачные и тестовые обращения считаются по пользователю, аккаунту и модели. Счётчик за 24 часа отражает только вызовы LifeOS, а не чужое использование ключа. OpenRouter `:free` показывает опубликованные лимиты 20 запросов в минуту и 50 в день на free account. Для Groq показывается только счётчик LifeOS: таблица Groq публикует базовые значения Developer tier, а фактические лимиты зависят от аккаунта и доступны в Console или ответных rate-limit headers. Эти Developer-tier числа не маркируются как бесплатная квота.

Gemini-подключение требует явного подтверждения пользователя, что проект работает на Free Tier. API-ключ не содержит самостоятельных параметров биллинга, а LifeOS не проверяет тариф Google Cloud; тест подключения также расходует один вызов квоты. Интерфейс не предлагает платный апгрейд и не считает подключение доказательством отключённого биллинга. Cerebras остаётся в каталоге как заблокированная карточка: Free Trial требует проверенный платёжный метод, даёт ограниченные кредиты на 30 дней и не имеет постоянно бесплатного тарифа. Сохранённые старые Cerebras-аккаунты не участвуют в fallback, а сервер блокирует подключение, выбор моделей, включение и перестановку таких аккаунтов. Custom endpoint валидируется на сервере: запрещаются HTTP, приватные/зарезервированные адреса, DNS-ответы с непубличным IP и редиректы; DNS-адреса фиксируются на время исходящего TLS-запроса. Локальные/private endpoints не поддерживаются.

Если все настроенные провайдеры отказали, Telegram и Mini App показывают безопасное объяснение причины: Gemini `402` или явный `payment_required` означает исчерпанные оплаченные кредиты; `429` — достигнутый лимит квоты/частоты, который не обязательно связан с оплатой; сетевой сбой, таймаут, `408`, `425` или `5xx` — временную недоступность API; ошибки аутентификации, доступа или модели — проблему конфигурации. При разных причинах отказа резерва сообщение перечисляет каждую по провайдеру. Текст ответа провайдера, ключи и содержимое запроса пользователю не раскрываются; неудачный разбор ничего не записывает, остаётся ручной ввод. Основание классификации: [ошибки Gemini API](https://ai.google.dev/gemini-api/docs/api-errors), [ограничения Gemini](https://ai.google.dev/gemini-api/docs/rate-limits), [ошибки Groq API](https://console.groq.com/docs/errors).

Ответ ИИ проверяется схемой Zod; дневные суммы и конвертация вычисляются кодом. Финансовой операции назначается категория по смыслу сообщения; если описание не даёт основания для более точной категории, используется «Прочее». Неотвеченное уточнение хранится как ограниченная текстовая история владельца с TTL 30 минут, передаётся в следующий разбор и очищается при появлении черновика или `/cancel`; истёкшая история очищается при следующем разборе. Еда и обычная финансовая операция сохраняются из черновика только после нажатия «Записать» в Telegram. Редактирование категории остаётся доступным для исправления ошибочного предложения; категория не должна запрашиваться в обычном сценарии. Mini App не показывает повторную панель подтверждения. Еда и расход из одного сообщения — всегда отдельные черновики: у каждого свои «Записать», «Исправить» и «Отменить», общая транзакция не используется. Если в сообщении несколько блюд/напитков и один общий расход, инструкция разбора формирует отдельный черновик с собственным КБЖУ для каждой позиции и отдельный финансовый черновик с `food=null`; всем позициям назначается один `occurredAt`. Каждый черновик имеет независимое подтверждение, общий расход не связан с конкретным блюдом и не дублируется. Используются таблицы `capture_drafts`, `nutrition_drafts` и `money_drafts`; тип `combined` в `capture_drafts` остался только для старых записей. После успеха бот называет сохранённые записи и значимые данные. Повторное подтверждение уже сохранённого черновика не создаёт повторную запись.

API-ключи хранятся как AES-256-GCM ciphertext в `ai_provider_profiles` (legacy) и `ai_provider_accounts`; браузеру возвращается только `hasApiKey`. Для шифрования обязателен серверный `AI_PROVIDER_ENCRYPTION_KEY` — base64-кодированные 32 случайных байта. Он не хранится в базе; потеря или несовместимая ротация делает ключи расшифровки недоступными. BYOK-аккаунты, ключи и счётчики исключены из резервной копии. Скрытая панель включает пользовательские счётчики и, если у legacy-владельца есть `GOOGLE_CLOUD_SERVICE_ACCOUNT_JSON` и `GOOGLE_CLOUD_PROJECT_ID`, метрики Gemini Cloud Monitoring.

Вход через OpenRouter (OAuth PKCE) — необязательное удобство в мастере подключения, ручной ввод ключа остаётся. `POST /api/ai/oauth/openrouter` (подпись `initData`) создаёт попытку в `ai_oauth_sessions` (хэш случайного `state`, зашифрованный `code_verifier`, TTL 10 минут, привязка к владельцу) и возвращает ссылку `https://openrouter.ai/auth`; Mini App открывает её через `Telegram.WebApp.openLink` и опрашивает `GET /api/ai/oauth/openrouter?id=`. Редирект OpenRouter приходит на `GET /api/ai/oauth/openrouter/callback` (в браузере нет сессии Telegram, доказательство — `state`): попытка забирается атомарно (одноразово), код обменивается на ключ через `POST /api/v1/auth/keys`, ключ проходит тот же путь проверки и шифрования, что и вставленный вручную; клиенту он не отдаётся. Адрес callback строится из `APP_URL` (нужен HTTPS). После успеха страница callback переходит по deep link обратно в Mini App (плюс кнопка «Вернуться в LifeOS»), а Mini App при возврате сразу проверяет статус. Документация Telegram не описывает встроенный браузер для Mini App: `openLink` — внешний. Поэтому кнопка входа пробует `window.open(url, "_blank")` (клиенты Telegram обычно показывают его во встроенном браузере) и при неудаче падает на `openLink`. Хелпер — `openAuthPage` в `openrouter-oauth-login.tsx`, откатывается одной правкой. Вход через Google/GitHub во встроенных браузерах может блокироваться (`disallowed_useragent`); запасной путь — ручной ключ.

Порядок бесплатных моделей провайдера в каталоге и предвыбор для нового аккаунта задаёт чистый модуль `src/domain/ai-model-ranking.ts`: vision выше текста, мусорные модели (embedding, audio, guard и т. п.) в конце, дальше правила провайдера, версия, размер и контекст из id, алфавит только последним тай-брейком. Новый провайдер включает лучшие до трёх vision-моделей и одну текстовую (без vision — три текстовые), остальные сохраняются выключенными; уже сохранённые выбор и порядок пользователя не меняются.

Справочные вопросы проходят отдельным read-only путём до разбора черновика. Ответы о балансе, тратах, КБЖУ и тренировке формируются из снимка данных; точные суммы и агрегаты выбирает код. Остальные вопросы получают ограниченный JSON-контекст снимка и обрабатываются теми же BYOK-профилями, без доступа к БД, команд записи или истории диалога. Вопрос не создаёт черновик и не изменяет сохранённую историю уточнения; обычные сообщения о еде и операциях остаются в сценарии записи.

Фото Telegram загружается на время обработки, с ограничением 8 МБ. Успешно обработанный Telegram update очищает сохранённое тело события; в журнале попыток остаются служебные поля. Реальное удаление данных на стороне Telegram или ИИ-провайдера проект не контролирует.

## Часовой пояс и сводки

Часовой пояс профиля определяется на знакомстве и настраивается в «Персонализации» (значение схемы `Europe/Chisinau` — только для существующих профилей); вес хранится как календарная дата (полдень UTC этой даты), операции — как момент времени; приложение группирует записи и отчёты по локальному дню. Дневная сводка по умолчанию уходит в 19:30, недельная — по воскресеньям в 19:30 по часовому поясу пользователя. Недельная сводка дополнительно считает средний вес за 7 локальных дней (`weeklyAverageWeight`) и при трёх и более замерах предлагает норму из `targetFromAverage`; кнопка `tgt:<ккал>-<белки>-<жиры>-<углеводы>` сохраняет её через `settings.save`, `tgt:keep` ничего не меняет. Эти значения соответствуют выбранному пользователем ориентиру на вечер и могут переопределяться `DAILY_SUMMARY_TIME` и `WEEKLY_SUMMARY_TIME` в формате `HH:MM`. Значения по умолчанию `19:30` указаны в `.env.example`.

Каждая текстовая сводка сохраняет прежний текст и получает inline-кнопку `web_app` на `/summary` с периодом и датой начала. HTML страницы не содержит личных данных: браузер загружает отчёт только через подписанный запрос к `/api/summary`. Агрегаты рассчитываются кодом по сохранённым операциям и курсам, с учётом включённых разделов; отсутствие записи питания не равно нулю. Советы готовятся при создании сводки (плановой или по `/summary`, не дольше 20 секунд, сводка уходит в любом случае) через настроенную BYOK-очередь, проверяются Zod и сохраняются в `summary_advice_cache` по владельцу и границам периода (версия формата в записи; кэш старой версии промпта игнорируется); страница при открытии только читает кэш, а если советов нет, предлагает кнопку «Получить советы». При отсутствии ИИ отчёт остаётся доступен. Провайдеру передаются числовые агрегаты: суммы в основных единицах валюты, названия категорий, общий баланс счетов, цель по весу и его динамика, сравнение с предыдущим периодом; без названий блюд, операций и упражнений, без Telegram ID; кэш хранит текст подтверждённых советов. Миграция `0024` применена в production.

Команда `/summary` отправляет прошлую завершённую неделю, `/summary day` — вчера, `/summary month` — прошлый календарный месяц в часовом поясе владельца; `/summary week` равнозначна команде без аргумента. Доступна после согласия, не чаще одного запроса за 30 секунд на владельца. Ручная отправка не записывает `notification_deliveries` и не отменяет доставку по расписанию; пустой период получает отдельное сообщение.

Cron-маршрут также проверяет сроки регулярных платежей и ждёт ручного подтверждения фактической оплаты. Интервал cron-job.org — каждые 30 минут: сводка уходит в окне `[время пользователя, +30 минут)`, зависшие update повторяются в течение получаса, а не суток. Чаще не ставить: Neon Free засыпает после 5 минут простоя, вызов чаще 5–15 минут держит базу активной круглые сутки и выжигает квоту около 100 CU-часов в месяц до остановки базы.

## Настройка и команды

Скопируйте `.env.example` в `.env`. Основные переменные:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | PostgreSQL для приложения, миграций и резервных копий |

| `TELEGRAM_OWNER_ID` | Необязательный Telegram ID, которому доступны метрики квот Gemini. Как запасной владелец данных и получателя сообщений больше не используется: профиль определяется только проверенным Telegram ID запроса |
| `TELEGRAM_WEBHOOK_SECRET` | Проверка входящих Telegram updates |
| `CRON_SECRET` | Защита `/api/cron`; рекомендуется случайная строка не короче 32 символов (при более слабой сервер пишет предупреждение в лог) |
| `GEMINI_MODEL` | Модель Gemini для метрик квот, по умолчанию `gemini-3.5-flash-lite` |
| `GOOGLE_CLOUD_SERVICE_ACCOUNT_JSON` | Необязательный JSON сервисного аккаунта только для чтения квот Gemini; хранить как секрет сервера |
| `GOOGLE_CLOUD_PROJECT_ID` | Необязательный проект Google Cloud для метрик; по умолчанию берётся из JSON сервисного аккаунта |
| `AI_PROVIDER_ENCRYPTION_KEY` | Обязателен для сохранения BYOK-профилей (ключи ИИ задаются только пользователями в Mini App; `GEMINI_API_KEY` и `GROQ_API_KEY` из окружения в production больше не используются): base64 от 32 случайных байт; не терять и не менять без процедуры перешифрования |
| `APP_URL` | HTTPS URL для `npm run telegram:register` |

Команды проекта объявлены в `package.json`:

| Команда | Назначение |
|---|---|
| `npm run dev`, `npm run build`, `npm run start` | Разработка, сборка и production-сервер Next.js |
| `npm run lint`, `npm run typecheck`, `npm test` | Статические проверки и тесты |

Резервная копия включает данные приложения и не включает технические строки Telegram updates и доставки уведомлений. Восстановление идёт одной транзакцией для Telegram ID из `--owner` или `TELEGRAM_OWNER_ID`: другие пользователи в базе не затрагиваются, а если профиль с этим ID уже есть, команда отказывает (409). Endpoint восстановления через веб не предусмотрен. Подробности — [operations.md](operations.md).

## Заголовки безопасности и устойчивость cron

- Все маршруты отдают `Content-Security-Policy` (только `frame-ancestors` для Telegram, `base-uri`, `object-src`, `form-action`), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` и `Strict-Transport-Security` (`src/server/security-headers.ts`). Полная политика `script-src` требует nonce и запланирована отдельно ([план релиза](release-plan.md)).
- `/api/cron` (`src/server/cron.ts`) обрабатывает владельцев независимо и пачками по три: сбой у одного (например, пользователь заблокировал бота) пишется в лог и не прерывает остальных; ответ содержит число сбоев. Порядок: напоминания и сводки (бюджет 10 с, остальные владельцы дождутся следующего вызова), очистка, затем повтор зависших update (не больше двух за вызов и только если до 57 с осталось не меньше 45 с). Update старше 6 часов не разбирается молча: пользователю в личном чате приходит просьба отправить сообщение заново. Повтор передаёт ИИ время сообщения, а не время разбора.
- Цепочка ИИ-провайдеров на один запрос (`src/server/ai/analyze.ts`) ограничена общим бюджетом 42 с (остаток передаётся в таймаут попытки, максимум 18 с), не более шести кандидатов; аккаунт, ответивший 429, пропускается на минуту (в памяти экземпляра). При исчерпании бюджета пользователь получает честное сообщение, а не вечное «Анализирую…».
- Сводки и напоминание о весе отправляются в окне `[время, время + SUMMARY_WINDOW_MINUTES)` (30 по умолчанию); дедупликация проверяется до сборки сводки.
- Ключи ИИ из окружения никогда не обслуживают пользователей; переменная `LIFEOS_ALLOW_ENV_AI_KEYS=1` существует только для тестов (`tests/setup.ts`).
- Команда в `executeCommand` без обработчика даёт ошибку компиляции (проверка исчерпанности по `never`), а не молчаливый успех.

## Ограничение частоты запросов

Счётчики с фиксированными окнами хранятся в таблице `rate_limit_counters` (`src/server/rate-limit.ts`). Лимиты на проверенный Telegram ID: команды и снимок по 120 в минуту, настройки ИИ и лимиты ИИ по 30 в минуту, экспорт 5 в час, сообщения боту 60 в минуту (сверх лимита update подтверждается и отбрасывается). Глобально: не более 60 новых профилей в час. При превышении API отвечает `429` с `Retry-After`. Если таблицы нет или база недоступна, лимитер пропускает запрос и пишет ошибку в лог. Старые счётчики удаляет cron.

## Согласие, экспорт и удаление данных

- Версия политики хранится в `src/domain/privacy.ts` (`PRIVACY_POLICY_VERSION`); принятая версия и время записаны в `owner_settings`. Отдельное согласие на данные о здоровье хранится в `health_consent_*` (`HEALTH_CONSENT_VERSION`) и отзывается в настройках. Согласие проверяет сервер: `executeCommand` и маршруты `/api/ai-providers`, `/api/ai-quotas` отвечают 403 без текущего согласия (`assertConsent`); исключения — `privacy.accept`, `privacy.health.*`, `account.delete`, снимок (bootstrap) и экспорт. Бот без согласия отвечает только просьбой принять его, кроме `/export` и `/delete`. Срок хранения черновиков и технических записей исполняет cron (`src/server/retention.ts`).
- `account.delete` (команда, подтверждение словом `УДАЛИТЬ`) удаляет строку `owner_settings`; все данные владельца удаляются каскадом по внешним ключам, счётчики лимитов, привязанные к Telegram ID, удаляются отдельно (`deleteOwnerData` в `src/server/lifeos.ts`, покрыто тестом на полном наборе данных). После удаления снимок не загружается, чтобы не создать пустой профиль.
- `POST /api/export` и команда бота `/export` отправляют JSON-копию данных файлом в личный чат (не чаще пяти раз в час); `GET /api/export` оставлен для скачивания.
- Cron удаляет технические записи `telegram_updates` старше 14 дней (`TELEGRAM_UPDATE_RETENTION_DAYS`).

## Структура серверного кода

- `src/server/commands/` — обработчики команд Mini App по доменам (`nutrition`, `finance`, `debts`, `gym`, `drafts`, `settings`); `index.ts` собирает реестр `commandHandlers` и функцию `dispatch`. Тип реестра требует обработчик для каждого типа команды из `src/domain/commands.ts`, поэтому новая команда без обработчика не компилируется.
- `src/server/lifeos.ts` — владелец профиля (`ensureOwner`), сборка снимка (`loadSnapshot`), разбор ИИ (`analyzeCapture`) и точка входа `executeCommand` (транзакция, блокировка владельца, затем `dispatch`).
- `src/server/gym-reports.ts` — статистика зала и поиск предыдущей тренировки через индексы; результат совпадает с исходным перебором (сверяется в `tests/gym-reports.test.ts`).
- `src/server/telegram/` — бот: `bot.ts` (только реэкспорты), `client.ts` (сборка grammY-бота и порядок регистрации), `middleware.ts` (согласие с политикой), `handlers/` (команды, сообщения, фото, кнопки, черновики), `updates.ts` (хранение и повтор событий), `notifications.ts` (напоминания, сводки, экспорт), `shared.ts`.
- Снимок отдаёт клиенту не больше `MAX_SNAPSHOT_FINANCE_ENTRIES` (1000) последних операций; балансы и отчёты считаются по всем.
