# Техническая основа LifeOS

Документ описывает устройство системы. Что проверено на реальных сервисах и что нет, записано в [status.md](status.md); развёртывание — в [deployment.md](deployment.md), эксплуатация — в [operations.md](operations.md), переменные окружения — в [configuration.md](configuration.md).

В `next.config.ts` выставлен `experimental.useTypeScriptCli: false`, чтобы Next.js использовал TypeScript API. Требуется Node.js `>=22`. Установка выполняется через `npm ci`.

В приложении нет отдельного сервера, Redis, банковской синхронизации или чужого движка. Исходные изображения еды передаются облачному ИИ во время разбора, но приложение не сохраняет их в собственной постоянной базе. Провайдер обрабатывает полученные данные по своим условиям; LifeOS не контролирует его хранение.

## Приложение и API

Интерфейс, серверные маршруты и доменная логика находятся в одном Next.js-проекте. На совместимых Telegram-клиентах Mini App после инициализации вызывает `requestFullscreen()`; при отсутствии поддержки остаётся обычное развёрнутое представление. Клиент читает `isFullscreen`, `safeAreaInset` и `contentSafeAreaInset` из Telegram WebApp API и обновляет их по событиям изменения fullscreen и safe area. В fullscreen шапка резервирует минимум 80 px сверху, а также учитывает безопасные отступы; обычное развёрнутое представление сохраняет компактную шапку. Пользователь обнаружил наложение меню Telegram на шапку в Android; исправление развернуто, визуальная проверка в Telegram WebView ещё нужна.

Основные вызовы Mini App требуют заголовок `Authorization: tma <Telegram initData>`; сервер сверяет подпись и срок данных и использует проверенный Telegram ID для выбора отдельного профиля. Клиентский `initDataUnsafe` сам по себе не используется для авторизации. Для API-проверки срок `initData` по умолчанию — 24 часа. `TELEGRAM_OWNER_ID` необязателен и задаёт только legacy-аккаунт для общих deployment ключей и квот Gemini.

| Метод и путь | Назначение | Доступ |
|---|---|---|
| `GET /api/snapshot?date=YYYY-MM-DD` | Данные выбранного дня, история и сводные отчёты | Telegram `initData` пользователя |
| `POST /api/commands` | Проверенная Zod команда, затем обновлённый снимок данных | Telegram `initData` пользователя |
| `GET /api/ai-providers` | Каталог провайдеров, собственные аккаунты, модели, состояние первичной настройки и единая очередь; API-ключи не возвращаются | Telegram `initData` пользователя; `Cache-Control: no-store` |
| `POST /api/ai-providers` | Подключение аккаунта с тестом ключа, изменение общей очереди моделей, завершение первичной настройки, приоритета/доступности аккаунта и обновление каталога | Telegram `initData` пользователя |
| `DELETE /api/ai-providers?id=...` | Удаление собственного аккаунта и зашифрованного ключа | Telegram `initData` пользователя |
| `GET /api/ai-quotas` | Счётчики запросов LifeOS и опубликованные квоты OpenRouter `:free`; legacy Gemini Cloud Monitoring добавляется отдельно | Telegram `initData` пользователя; `Cache-Control: no-store` |
| `GET /api/health` | Проверка доступности: статус и версия, без секретов и без обращения к базе | Не требуется |
| `POST /api/telegram` | Приём Telegram update, сохранение события и обработка бота | Секретный заголовок Telegram webhook |
| `GET` или `POST /api/cron` | Повтор обработок, напоминания и ежедневная/недельная сводка | `Authorization: Bearer <CRON_SECRET>` |
| `GET /api/export` | JSON-копия данных текущего пользователя | Telegram `initData` пользователя |

Маршруты заданы в `src/app/api/`. Команды и их поля — в `src/domain/commands.ts`. Бот отвечает на `/start`, `/help`, `/today`, `/export` и `/cancel`, а также обрабатывает сообщения, фотографии и кнопки подтверждения.

## Данные и миграции

Схема `src/db/schema.ts` описывает профиль, Telegram-события, черновики, питание, финансы (счета, категории, курсы, операции, регулярные платежи, планы покупок, долги), тренировки и ИИ-профили; история изменений — SQL-файлы в `drizzle/` и [database.md](database.md). Все пользовательские строки ограничены ID профиля.

Для планов будущих покупок реализована отдельная модель, изолированная по Telegram-профилю и отделённая от записанных операций. Пока покупка не подтверждена как расход, планируемая сумма не участвует в балансе и отчётах.

Долг хранит человека, направление (`i_owe` или `owed_to_me`), первоначальную сумму в основной валюте, необязательный срок и заметку. Остаток вычисляется как первоначальная сумма минус отдельные записи возвратов. Каждая запись возврата связана с финансовой операцией; старый долг создаётся без исторического движения счёта. Явные сообщения бота создают черновик и требуют нажатия «Записать»; Mini App использует отдельные формы создания и возврата. Cron ежедневно напоминает об открытом долге начиная с даты срока, уведомление за каждый локальный день дедуплицируется ключом доставки. Схема `0006` уже развернута; сами операции долгов требуют пользовательской сквозной проверки.

Все пользовательские данные связаны с отдельным Telegram-профилем через `ownerId`, ссылающийся на `ownerSettings`. Telegram ID проверяется подписью Bot API перед каждой Mini App операцией и при обработке личного чата. Суммы хранятся в исходной валюте. Внутренний код `PRB` означает приднестровский рубль, а не российский `RUB`.

История КБЖУ для календаря строится из всех сохранённых записей питания и группируется по локальной дате владельца. Новая таблица и миграция не нужны: `nutritionDays` содержит каждую дату с едой и текущую дату, даже если в ней пока нет записей. Отчёт расходов `expenseDays` сохраняет отдельное ограничение последними 31 днями. Календарь не трактует отсутствие записей как нулевое потребление.

Валюта — код из 3–5 латинских букв (`^[A-Z]{3,5}$`, ISO или свой). Основная валюта (`owner_settings.base_currency`) задаётся валютой первого счёта и дальше не меняется; итоги, планы и долги считаются в ней. Операция в неосновной валюте хранит снимок ручного курса (`rate_to_base`, единиц основной валюты за единицу операции), действовавшего для времени этой операции; курсы лежат в `exchange_rates` по валюте и дате начала действия. При вводе курса задаётся дата начала его действия; новый курс не переоценивает уже сохранённые операции. Валютного сервиса и синхронизации остатков нет.

Финансовая операция хранит положительную сумму в minor units; знак отображения определяется типом операции: расход — минус, доход — плюс. Эта визуальная подпись не меняет формулу остатка счёта. Обзор вкладки «Финансы» сначала показывает расчётный баланс основного счёта, а расходы за день и месяц располагает ниже.

`npm run db:generate` создаёт миграцию по Drizzle-схеме; `npm run db:migrate` применяет её к `DATABASE_URL`. Состояние миграций в production: [status.md](status.md); процедура применения: [deployment.md](deployment.md) (`drizzle-kit migrate` на этом проекте завершается без сообщения, поэтому SQL применяется транзакцией вручную).

## Сообщения, ИИ и подтверждения

Telegram webhook проверяет секрет, сохраняет update в БД и возвращает ответ Telegram; обработку продолжает Next.js `after()` внутри времени жизни функции. Production webhook зарегистрирован и шесть Telegram updates получили статус `processed` в Neon. Ошибки и зависшие события могут быть повторены cron-маршрутом до трёх попыток. `after()` ограничен серверной функцией и не является долговечной очередью; повторы и обработка в Telegram WebView отдельно не проверялись.

Новый каталог предоставляет компактный список Gemini, Groq, OpenRouter, Cerebras и расширенного OpenAI-compatible режима. Карточки используют официальные логотипы и ссылки на страницы получения API-ключей. `/start` объясняет роль API-ключа и открывает Mini App; при первом запуске Mini App показывает мастер из трёх шагов (объяснение ключа, рекомендованный сервис с инструкцией и полем ключа, примеры сообщений), который подключает аккаунт под именем сервиса, принимает автоматически выбранные модели и очередь и сразу завершает онбординг. Описанные ниже экраны каталога, моделей и очереди — расширенные настройки. После выбора провайдера отдельный экран объясняет его условия и подключение. Ключ проверяется коротким тестовым запросом до шифрованного сохранения; после успеха открывается отдельный экран моделей, где все обнаруженные подходящие модели включены по умолчанию. Следующий отдельный экран задаёт общую очередь моделей со всех аккаунтов и провайдеров. После первичного онбординга этот набор экранов открывается повторно отдельной вкладкой с шестерёнкой в нижней навигации; заголовок LifeOS не является кнопкой. `ai_provider_model_selections.sort_order` хранит именно этот порядок; один выбранный модельный профиль разворачивается сервером в аккаунтные кандидаты, а порядок аккаунтов служит резервом при одинаковой модели. Новый профиль добавляет ранее неизвестные модели в конец очереди; при удалении профиля модели без оставшихся подключений очищаются из очереди. `owner_settings.ai_onboarding_completed` позволяет пройти онбординг один раз, а `ai_model_queue_initialized` отмечает первичное включение доступных моделей. Бесплатные модели фильтруются по правилам провайдера: актуальный allowlist Gemini/Groq и OpenRouter `:free` с нулевой ценой. Каталог OpenRouter запрашивается с `max_price=0`; результат дополнительно проверяется по суффиксу `:free` и нулевой цене ввода/вывода. У Gemini запрос списка моделей использует `x-goog-api-key`, а OpenAI-compatible запрос генерации — `Authorization: Bearer`; эти заголовки намеренно разделены. При сбое приложение пробует следующую модель и её подходящие аккаунты; для фотографии подходят только модели с заявленной поддержкой изображений. Успешные, неудачные и тестовые обращения считаются по пользователю, аккаунту и модели. Счётчик за 24 часа отражает только вызовы LifeOS, а не чужое использование ключа. OpenRouter `:free` показывает опубликованные лимиты 20 запросов в минуту и 50 в день на free account. Для Groq показывается только счётчик LifeOS: таблица Groq публикует базовые значения Developer tier, а фактические лимиты зависят от аккаунта и доступны в Console или ответных rate-limit headers. Эти Developer-tier числа не маркируются как бесплатная квота.

Gemini-подключение требует явного подтверждения пользователя, что проект работает на Free Tier. API-ключ не содержит самостоятельных параметров биллинга, а LifeOS не проверяет тариф Google Cloud; тест подключения также расходует один вызов квоты. Интерфейс не предлагает платный апгрейд и не считает подключение доказательством отключённого биллинга. Cerebras остаётся в каталоге как заблокированная карточка: Free Trial требует проверенный платёжный метод, даёт ограниченные кредиты на 30 дней и не имеет постоянно бесплатного тарифа. Сохранённые старые Cerebras-аккаунты не участвуют в fallback, а сервер блокирует подключение, выбор моделей, включение и перестановку таких аккаунтов. Custom endpoint валидируется на сервере: запрещаются HTTP, приватные/зарезервированные адреса, DNS-ответы с непубличным IP и редиректы; DNS-адреса фиксируются на время исходящего TLS-запроса. Локальные/private endpoints не поддерживаются. Legacy Gemini/Groq ключи окружения добавляются в fallback только для Telegram ID из `TELEGRAM_OWNER_ID`.

Если все настроенные провайдеры отказали, Telegram и Mini App показывают безопасное объяснение причины: Gemini `402` или явный `payment_required` означает исчерпанные оплаченные кредиты; `429` — достигнутый лимит квоты/частоты, который не обязательно связан с оплатой; сетевой сбой, таймаут, `408`, `425` или `5xx` — временную недоступность API; ошибки аутентификации, доступа или модели — проблему конфигурации. При разных причинах отказа резерва сообщение перечисляет каждую по провайдеру. Текст ответа провайдера, ключи и содержимое запроса пользователю не раскрываются; неудачный разбор ничего не записывает, остаётся ручной ввод. Основание классификации: [ошибки Gemini API](https://ai.google.dev/gemini-api/docs/api-errors), [ограничения Gemini](https://ai.google.dev/gemini-api/docs/rate-limits), [ошибки Groq API](https://console.groq.com/docs/errors).

Ответ ИИ проверяется схемой Zod; дневные суммы и конвертация вычисляются кодом. Финансовой операции назначается категория по смыслу сообщения; если описание не даёт основания для более точной категории, используется «Прочее». Неотвеченное уточнение хранится как ограниченная текстовая история владельца с TTL 30 минут, передаётся в следующий разбор и очищается при появлении черновика или `/cancel`; истёкшая история очищается при следующем разборе. Еда и обычная финансовая операция сохраняются из черновика только после нажатия «Записать» в Telegram. Редактирование категории остаётся доступным для исправления ошибочного предложения; категория не должна запрашиваться в обычном сценарии. Mini App не показывает повторную панель подтверждения. Если сообщение содержит одну позицию еды и связанный расход, еда и расход остаются в одном черновике и сохраняются одной транзакцией по одному подтверждению. Если в сообщении несколько блюд/напитков и один общий расход, инструкция разбора должна сформировать отдельный черновик с собственным КБЖУ для каждой позиции и отдельный финансовый черновик с `food=null` для общего расхода; всем позициям назначается один `occurredAt`. Каждый черновик имеет независимое подтверждение, общий расход не связан с конкретным блюдом и не дублируется. Это использует существующие `captureDrafts`, `nutritionDrafts` и `moneyDrafts`, не требует новой таблицы, миграции или изменения схемы. После успеха бот называет сохранённые записи и значимые данные, а для черновика с едой и расходом — оба пункта. Повторное подтверждение уже сохранённого черновика не создаёт повторную запись.

API-ключи хранятся как AES-256-GCM ciphertext в `ai_provider_profiles` (legacy) и `ai_provider_accounts`; браузеру возвращается только `hasApiKey`. Для шифрования обязателен серверный `AI_PROVIDER_ENCRYPTION_KEY` — base64-кодированные 32 случайных байта. Он не хранится в базе; потеря или несовместимая ротация делает ключи расшифровки недоступными. BYOK-аккаунты, ключи и счётчики исключены из резервной копии. Скрытая панель включает пользовательские счётчики и, если у legacy-владельца есть `GOOGLE_CLOUD_SERVICE_ACCOUNT_JSON` и `GOOGLE_CLOUD_PROJECT_ID`, метрики Gemini Cloud Monitoring.

Справочные вопросы проходят отдельным read-only путём до разбора черновика. Ответы о балансе, тратах, КБЖУ и тренировке формируются из снимка данных; точные суммы и агрегаты выбирает код. Остальные вопросы получают ограниченный JSON-контекст снимка и обрабатываются теми же BYOK-профилями (либо legacy Gemini/Groq для настроенного владельца), без доступа к БД, команд записи или истории диалога. Вопрос не создаёт черновик и не изменяет сохранённую историю уточнения; обычные сообщения о еде и операциях остаются в сценарии записи.

Фото Telegram загружается на время обработки, с ограничением 8 МБ. Успешно обработанный Telegram update очищает сохранённое тело события; в журнале попыток остаются служебные поля. Реальное удаление данных на стороне Telegram или ИИ-провайдера проект не контролирует.

## Часовой пояс и сводки

Часовой пояс профиля определяется на знакомстве и настраивается в «Персонализации» (значение схемы `Europe/Chisinau` — только для существующих профилей); вес хранится как календарная дата (полдень UTC этой даты), операции — как момент времени; приложение группирует записи и отчёты по локальному дню. Дневная сводка по умолчанию уходит в 19:30, недельная — по воскресеньям в 19:30 по часовому поясу пользователя. Недельная сводка дополнительно считает средний вес за 7 локальных дней (`weeklyAverageWeight`) и при трёх и более замерах предлагает норму из `targetFromAverage`; кнопка `tgt:<ккал>-<белки>-<жиры>-<углеводы>` сохраняет её через `settings.save`, `tgt:keep` ничего не меняет. Эти значения соответствуют выбранному пользователем ориентиру на вечер и могут переопределяться `DAILY_SUMMARY_TIME` и `WEEKLY_SUMMARY_TIME` в формате `HH:MM`. Значения по умолчанию `19:30` указаны в `.env.example`.

Cron-маршрут также проверяет сроки регулярных платежей и ждёт ручного подтверждения фактической оплаты. Целевой интервал cron-job.org — каждые 30 минут (раньше стоял один вызов в сутки в 19:30): сводка уходит в окне `[время пользователя, +30 минут)`, зависшие update повторяются в течение получаса, а не суток. Чаще не ставить: Neon Free засыпает после 5 минут простоя, вызов чаще 5–15 минут держит базу активной круглые сутки и выжигает квоту около 100 CU-часов в месяц до остановки базы. Ручной тест вернул `200 OK`, автоматическая доставка сводок и напоминаний не проверена.

## Настройка и команды

Скопируйте `.env.example` в `.env`. Основные переменные:

| Переменная | Назначение |
|---|---|
| `DATABASE_URL` | PostgreSQL для приложения, миграций и резервных копий |
| `TELEGRAM_BOT_TOKEN` | Авторизация Telegram Bot API и проверка Mini App `initData` |
| `TELEGRAM_OWNER_ID` | Необязательный Telegram ID, которому доступны метрики квот Gemini. Как запасной владелец данных и получателя сообщений больше не используется: профиль определяется только проверенным Telegram ID запроса |
| `TELEGRAM_WEBHOOK_SECRET` | Проверка входящих Telegram updates |
| `CRON_SECRET` | Защита `/api/cron`; рекомендуется случайная строка не короче 32 символов (при более слабой сервер пишет предупреждение в лог) |
| `GEMINI_MODEL` | Модель Gemini для метрик квот, по умолчанию `gemini-3.5-flash-lite` |
| `GOOGLE_CLOUD_SERVICE_ACCOUNT_JSON` | Необязательный JSON сервисного аккаунта только для чтения квот Gemini; хранить как секрет сервера |
| `GOOGLE_CLOUD_PROJECT_ID` | Необязательный проект Google Cloud для метрик; по умолчанию берётся из JSON сервисного аккаунта |
| `AI_PROVIDER_ENCRYPTION_KEY` | Обязателен для сохранения BYOK-профилей (ключи ИИ задаются только пользователями в Mini App; `GEMINI_API_KEY` и `GROQ_API_KEY` из окружения в production больше не используются): base64 от 32 случайных байт; не терять и не менять без процедуры перешифрования |
| `APP_URL` | HTTPS URL для `npm run telegram:register` |

Команды проекта объявлены в `package.json`:

| Команда | Назначение |
|---|---|
| `npm run dev`, `npm run build`, `npm run start` | Разработка, сборка и production-сервер Next.js |
| `npm run lint`, `npm run typecheck`, `npm test` | Статические проверки и тесты |
| `npm run db:generate`, `npm run db:migrate` | Генерация и применение миграции |
| `npm run telegram:register` | Установка webhook через Telegram Bot API |

Резервная копия включает данные приложения и не включает технические строки Telegram updates и доставки уведомлений. Восстановление разрешено лишь для пустого профиля владельца и совпадающего `TELEGRAM_OWNER_ID`; endpoint восстановления через веб не предусмотрен. Реальный экспорт/restore на Neon нужно проверить до личного запуска.

## Заголовки безопасности и устойчивость cron

- Все маршруты отдают `Content-Security-Policy` (только `frame-ancestors` для Telegram, `base-uri`, `object-src`, `form-action`), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy` и `Strict-Transport-Security` (`src/server/security-headers.ts`). Полная политика `script-src` требует nonce и запланирована отдельно ([план релиза](release-plan.md)).
- `/api/cron` (`src/server/cron.ts`) обрабатывает владельцев независимо и пачками по три: сбой у одного (например, пользователь заблокировал бота) пишется в лог и не прерывает остальных; ответ содержит число сбоев. Порядок: напоминания и сводки (бюджет 10 с, остальные владельцы дождутся следующего вызова), очистка, затем повтор зависших update (не больше двух за вызов и только если до 57 с осталось не меньше 45 с). Update старше 6 часов не разбирается молча: пользователю в личном чате приходит просьба отправить сообщение заново. Повтор передаёт ИИ время сообщения, а не время разбора.
- Цепочка ИИ-провайдеров на один запрос (`src/server/ai/analyze.ts`) ограничена общим бюджетом 42 с (остаток передаётся в таймаут попытки, максимум 18 с), не более шести кандидатов; аккаунт, ответивший 429, пропускается на минуту (в памяти экземпляра). При исчерпании бюджета пользователь получает честное сообщение, а не вечное «Анализирую…».
- Сводки и напоминание о весе отправляются в окне `[время, время + SUMMARY_WINDOW_MINUTES)` (30 по умолчанию); дедупликация проверяется до сборки сводки.
- Ключи ИИ из окружения никогда не обслуживают пользователей; переменная `LIFEOS_ALLOW_ENV_AI_KEYS=1` существует только для тестов (`tests/setup.ts`).
- Команда в `executeCommand` без обработчика даёт ошибку компиляции (проверка исчерпанности по `never`), а не молчаливый успех.

## Ограничение частоты запросов

Счётчики с фиксированными окнами хранятся в таблице `rate_limit_counters` (`src/server/rate-limit.ts`, миграция `0014`). Лимиты на проверенный Telegram ID: команды и снимок по 120 в минуту, настройки ИИ и лимиты ИИ по 30 в минуту, экспорт 5 в час, сообщения боту 60 в минуту (сверх лимита update подтверждается и отбрасывается). Глобально: не более 60 новых профилей в час. При превышении API отвечает `429` с `Retry-After`. Если таблицы нет или база недоступна, лимитер пропускает запрос и пишет ошибку в лог. Старые счётчики удаляет cron.

## Согласие, экспорт и удаление данных

- Версия политики хранится в `src/domain/privacy.ts` (`PRIVACY_POLICY_VERSION`); принятая версия и время записаны в `owner_settings` (миграция `0015`). Пока версия не принята, Mini App показывает экран согласия, а бот отвечает только просьбой принять политику. Смена версии заставляет принять политику заново.
- `account.delete` (команда, подтверждение словом `УДАЛИТЬ`) удаляет строку `owner_settings`; все данные владельца удаляются каскадом по внешним ключам, счётчики лимитов, привязанные к Telegram ID, удаляются отдельно (`deleteOwnerData` в `src/server/lifeos.ts`, покрыто тестом на полном наборе данных). После удаления снимок не загружается, чтобы не создать пустой профиль.
- `POST /api/export` и команда бота `/export` отправляют JSON-копию данных файлом в личный чат (не чаще пяти раз в час); `GET /api/export` оставлен для скачивания.
- Cron удаляет технические записи `telegram_updates` старше 14 дней (`TELEGRAM_UPDATE_RETENTION_DAYS`).

## Структура серверного кода

- `src/server/commands/` — обработчики команд Mini App по доменам (`nutrition`, `finance`, `debts`, `gym`, `drafts`, `settings`); `index.ts` собирает реестр `commandHandlers` и функцию `dispatch`. Тип реестра требует обработчик для каждого типа команды из `src/domain/commands.ts`, поэтому новая команда без обработчика не компилируется.
- `src/server/lifeos.ts` — владелец профиля (`ensureOwner`), сборка снимка (`loadSnapshot`), разбор ИИ (`analyzeCapture`) и точка входа `executeCommand` (транзакция, блокировка владельца, затем `dispatch`).
- `src/server/gym-reports.ts` — статистика зала и поиск предыдущей тренировки через индексы; результат совпадает с исходным перебором (сверяется в `tests/gym-reports.test.ts`).
- `src/server/telegram/` — бот: `bot.ts` (только реэкспорты), `client.ts` (сборка grammY-бота и порядок регистрации), `middleware.ts` (согласие с политикой), `handlers/` (команды, сообщения, фото, кнопки, черновики), `updates.ts` (хранение и повтор событий), `notifications.ts` (напоминания, сводки, экспорт), `shared.ts`.
- Снимок отдаёт клиенту не больше `MAX_SNAPSHOT_FINANCE_ENTRIES` (1000) последних операций; балансы и отчёты считаются по всем.
