# План реализации: что осталось проверить

Что реализовано в коде и что проверено на реальных сервисах, описано в [статусе](status.md); история изменений — в [CHANGELOG](../CHANGELOG.md). Эксплуатационный план до релиз-кандидата — в [release-plan.md](release-plan.md), краткая дорожная карта — в [roadmap.md](roadmap.md). Этот документ — перечень сквозных проверок, без которых приложение нельзя называть готовым к повседневному использованию.

## Принятый технический контур

- Next.js App Router + TypeScript; Mini App и серверные обработчики в одном проекте.
- Production размещается в Vercel; база — Neon Serverless PostgreSQL через Drizzle и SQL-миграции из `drizzle/`. Preview-деплои защищены.
- grammY webhook: сервер проверяет секрет webhook и Telegram `initData`, затем изолирует данные по проверенному Telegram ID.
- Zod проверяет команды и структуру ответа ИИ. Каталог Gemini, Groq и OpenRouter показывает доступные бесплатные модели; пользователь выбирает модели и вручную расставляет их в общей очереди. Профили одной модели остаются fallback-аккаунтами в своём порядке. Ключи шифруются перед записью в БД. Расширенный OpenAI-compatible endpoint остаётся на усмотрение пользователя и не имеет проверяемой тарифной категории.
- Gemini требует подтверждения Free Tier: статус биллинга проекта нельзя определить по API-ключу. Cerebras не подключается: его Free Trial требует проверенный платёжный метод.
- Сводки по умолчанию уходят ежедневно в 19:30 и по воскресеньям в 19:30 по часовому поясу пользователя; время и частоту пользователь меняет в настройках, серверные значения по умолчанию переопределяются переменными `DAILY_SUMMARY_TIME` и `WEEKLY_SUMMARY_TIME` (см. [конфигурацию](configuration.md)).
- Изображения не хранятся в постоянной базе LifeOS.

Точные зависимости — в `package.json` и `package-lock.json`; Node.js `>=22`. Переменные окружения — в [конфигурации](configuration.md), API и устройство — в [архитектуре](architecture.md), развёртывание — в [deployment.md](deployment.md).

## Оставшаяся проверка и запуск

### 1. Проверить питание на реальных данных

- Реальные текстовые и фото-сценарии: этикетки, местные продукты, несколько приёмов пищи, уточнение предыдущего черновика.
- Приблизительная оценка остаётся помеченной в сохранённом дневнике.
- Отсутствие или ошибка ИИ не теряет пользовательский ввод; ручная запись работает.
- Расчёт редактируемой цели на параметрах реального пользователя; оценка не выдаётся за медицинскую рекомендацию.

### 2. Проверить финансовые сценарии

- Каждая обычная чат-операция сначала предлагается как черновик; запись происходит только после «Записать».
- Сохранение исходной валюты и снимка ручного курса на время операции; новое значение курса не меняет сохранённую историю.
- Неизвестная категория, учёт дохода, регулярный платёж, ручной курс неосновной валюты, отчёты.
- Планы покупок: создание в Mini App и командой `план <название> <сумма>`, запись покупки с исправлением суммы, закрытие плана, отсутствие влияния незаписанных планов на баланс и отчёты.
- Долги (в основной валюте владельца): оба направления, несколько долгов у одного человека, частичный возврат со связанной финансовой записью, старый остаток без задней операции, обязательное подтверждение чатового черновика, ежедневные напоминания до закрытия.

### 3. Проверить журнал тренировок

- Таймер отдыха и продолжение текущей тренировки.
- Поиск, замена и сортировка встроенных и пользовательских упражнений.
- Подсказка о возможном повышении нагрузки; план автоматически не меняется.
- Вес/повторения, кардио время/дистанция, перезагрузка во время тренировки, просмотр прогресса.

### 4. Подключить и проверить сервисы

- Подключение провайдеров ИИ на реальных ключах (Gemini только после проверки Free Tier в AI Studio и подтверждения в Mini App; Groq, OpenRouter, свой endpoint): проверка ключа, выбор бесплатных моделей, ручной порядок резервов, переключение при лимите и ошибке, отсутствие автоматического добавления платных моделей; для фото — fallback только на модели с поддержкой изображений.
- Метрики квот Gemini через Google Cloud Monitoring: сервисный аккаунт с `roles/monitoring.viewer`, JSON только в переменной `GOOGLE_CLOUD_SERVICE_ACCOUNT_JSON` Production; ключ не передавать в чат.
- Фактическая доставка сводок и напоминаний через cron-job.org для защищённого вызова `/api/cron`.
- Mini App в Telegram iOS и Android WebView: safe area, клавиатура, полноэкранный режим, кнопка «Назад».
- Повтор зависших Telegram updates, экспорт и восстановление резервной копии (см. [эксплуатацию](operations.md)).
- Изоляция данных на втором Telegram-аккаунте.

### 5. Провести личную неделю

После настройки всех трёх модулей проверить на данных владельца, что он понимает, куда уходят расходы, видит недобор КБЖУ и замечает изменения тренировочных результатов. По итогам исправить реальные неудобства и обновить [статус](status.md).

## Команды из `package.json`

```bash
npm ci
cp .env.example .env
npm run dev
npm run lint
npm run typecheck
npm test
npm run build
npm run db:generate
npm run db:migrate
npm run telegram:register
npm run backup:export -- ./lifeos-backup.json
npm run backup:restore -- ./lifeos-backup.json
```

`db:migrate`, регистрация webhook и резервные копии требуют заполненных переменных окружения; регистрация webhook выполняет внешний вызов Telegram Bot API. Порядок применения миграций на production и регистрации webhook описан в [deployment.md](deployment.md). Restore принимает копию для совпадающего `TELEGRAM_OWNER_ID` и пустого профиля.

## Готовность к повседневному использованию

Первая версия считается готовой, когда все три модуля сохраняют данные в подключённой базе, согласованные сценарии работают из Telegram, ошибки ИИ не теряют ввод, таймер и журнал пригодны в реальной тренировке, расписание доставляет сводки, а экспорт и восстановление проверены. После этого нужна неделя использования для проверки трёх ожидаемых результатов из [продуктовых требований](product.md). До закрытия этих критериев не обозначать приложение как готовое.
