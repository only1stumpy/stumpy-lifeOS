# Аудит архитектуры, модульности и SOLID

Ветка `docs/audit-release-prep`, версия приложения 0.22.0. Аудит статический: код читался, приложение и тесты не запускались. Всё, что не подтверждено чтением кода, помечено «не проверено». Номера строк относятся к состоянию рабочей копии на момент аудита.

## 1. Сводка

Фундамент крепкий. `src/domain` чистый (в нём нет импортов из `server`, `db`, `components`, `app`). Компоненты не импортируют `server` и `db`. Единый контракт команд на Zod (`src/domain/commands.ts`) используют и Mini App, и бот. Схема БД содержит составные внешние ключи `(id, owner_id)`, которые на уровне БД не дают связать данные разных владельцев. Команды выполняются в транзакции с `SELECT ... FOR UPDATE` по строке владельца, то есть сериализуются по пользователю. Все миграции прогоняются в PGlite (`tests/backup.test.ts`).

Слабое место одно: прикладной слой собран в три «божественных» файла, а тестового шва в нём нет.

- `src/server/lifeos.ts` (883 строки): `executeCommand` на ~45 веток, чтение снимка, сценарии долгов, ИИ-разбор.
- `src/server/telegram/bot.ts` (1163 строки): маршрутизация, SQL, бизнес-правила, очередь апдейтов, уведомления.
- `src/components/editor/editor.tsx` (1101 строка) и `lifeos-app.tsx` (1044 строки).

Конкретные риски для релиза:
1. Один сбойный получатель роняет весь cron (A2).
2. Очередь нужных миграций 0012 и 0013 на production не подтверждена (A12).
3. Слой команд (`executeCommand`, `loadSnapshot`) не покрыт тестами совсем (A5).
4. Запрет `TELEGRAM_OWNER_ID` как запасного владельца действует только по соглашению (A4).

## 3. Что сделано хорошо

- **Чистый домен.** В `src/domain` нет импортов из `server`, `db`, `components`, `app` (проверено поиском). Деньги в целых minor-единицах с BigInt (`domain/math.ts:29-49`), `convertToBaseMinor` не использует числа с плавающей точкой.
- **Единый контракт команд.** `commandSchema` (`domain/commands.ts`) — дискриминированный union на Zod; бот и Mini App проходят через один `executeCommand`, правило «Еда и расход из одного сообщения — отдельные черновики» реализовано в одном месте (`lifeos.ts:527-529`).
- **Изоляция владельцев в двух слоях.** Запросы в коде фильтруются по `owner_id` (поиск неотфильтрованных `where` в `lifeos.ts`, `bot.ts`, `provider-accounts.ts` нашёл только запросы по идентификаторам, уже подтверждённым с фильтром владельца), а в схеме — составные внешние ключи `(id, owner_id[, currency/type])` (`schema.ts:257-262`, `drizzle/0000:335-367`), поэтому ошибка в коде не свяжет строки разных пользователей. `AsyncLocalStorage` (`owner-context.ts`) не даёт `owner_id` попасть в запрос из тела запроса.
- **Транзакции и конкурентность.** Блокировка строки владельца на каждую команду (`lifeos.ts:552-553`), `FOR UPDATE` в перестановках, идемпотентные `ON CONFLICT` (`weight.save`, курсы, цели), безопасная перестановка через временную позицию (`lifeos.ts:772-777`), идемпотентный `draft.confirm`, дедупликация апдейтов Telegram (`telegram_updates_update_id_unique`) и уведомлений (`notification_deliveries_owner_key_unique`).
- **Схема БД.** CHECK на суммы, валюты, статусы; частичный уникальный индекс «один счёт по умолчанию» (`schema.ts:355`); индексы под основные выборки; `ON DELETE RESTRICT` там, где нужны учётные записи.
- **Миграции.** Упорядочены (журнал 0–13), последовательно применяются в PGlite-тесте (`tests/backup.test.ts:39-61`), содержат бэкфилл с проверкой (`0001`).
- **Безопасный ИИ-слой.** `safe-fetch.ts` (SSRF-защита для пользовательского endpoint), ключи шифруются AES-256-GCM, ответ провайдера валидируется Zod, ошибки провайдера сводятся к безопасным категориям.
- **Внедрение зависимостей там, где оно сделано.** `backup.ts` принимает `BackupExecutor`; функции `tx`-first в `lifeos.ts` (`category`, `account`, `saveDebtTransfer`) принимают транзакцию, что уже позволило написать тест с PGlite.
- **Единственный маршрут команд и снимка** (`/api/commands`, `/api/snapshot`) — малая поверхность для безопасности и совместимости.

## 4. Рекомендуемая целевая архитектура

Принцип: тот же стек (Next.js, grammY, Drizzle, Zod), без нового бэкенда и без внешнего DI-контейнера. Вертикальные модули внутри слоёв, зависимости только вниз.

```
src/
  domain/                      # чистая логика, без process.env и без инфраструктуры
    nutrition/  finance/  gym/ # правила, форматы, схемы команд модуля
    commands.ts                # собирается из схем модулей
    modules.ts  math.ts  ...
  lib/
    errors.ts                  # AppError с code
    format.ts                  # общие форматтеры (pluralize, подписи сумм)
  db/
    client.ts                  # getDb() + возможность подставить базу в тестах
    schema.ts
  server/
    owner.ts                   # ensureOwner, owner-context (без запасного владельца)
    http.ts                    # requireOwner, authedRoute, errorResponse
    app/                       # слой приложения (сценарии)
      execute-command.ts       # диспетчер + блокировка владельца
      handlers/{settings,nutrition,finance,gym,drafts}.ts
      queries/{snapshot,nutrition,finance,gym}.ts   # читалки по модулям
      capture.ts               # analyzeCapture, черновики
    ai/
      adapter.ts               # интерфейс провайдера
      openai-compatible.ts  safe-fetch.ts  catalog.ts  accounts.ts  crypto.ts
      analyze.ts               # только оркестрация fallback
    telegram/
      bot.ts                   # сборка Bot и регистрация
      handlers/{commands,callbacks,messages}.ts
      updates-queue.ts         # приём, захват, повтор
      notifications.ts         # сводки, напоминания, дедупликация
      auth.ts  reference.ts  confirmation.ts
  app/api/...                  # тонкие маршруты: authedRoute(handler)
  components/
    editor/  # реестр kind → компонент формы
    ...
tests/
  integration/                 # PGlite: команды, изоляция владельцев, очередь
```

Правила зависимостей, которые стоит закрепить линтером: `components → domain, lib`; `app/api → server`; `server/telegram → server/app → db, domain`; `domain → lib` (и больше ничего); `db → lib`.

Новый модуль в этой схеме — это каталог `domain/<m>`, файл `server/app/handlers/<m>.ts`, читалка в `queries/`, запись в `LIFE_MODULES` и экран; остальное не трогается. Сейчас то же добавление затрагивает не менее 12 файлов (`modules.ts`, `welcome.ts`, `bot.ts` в пяти местах, `cron/route.ts`, `reference.ts`, `analyze.ts`, onboarding, personalization, `lifeos-app.tsx`, `lifeos.ts`, `backup.ts`).
