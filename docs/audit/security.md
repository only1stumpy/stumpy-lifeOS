# Аудит безопасности Stumpy LifeOS

Дата: 2026-11-15. Ветка: `docs/audit-release-prep`, версия `0.22.0`. Метод: статический разбор кода (чтение исходников, `npm audit --omit=dev`, поиск паттернов секретов в `git grep` и истории). Ничего не запускалось против production, динамических тестов и сетевых запросов к сервисам не было. Всё, что зависит от настроек Vercel, Neon, Telegram и cron-job.org (не от кода), помечено «не проверено».

## Сводка

**Общая оценка: средний риск; для закрытого запуска с несколькими доверенными пользователями приемлемо, для публичного запуска нужны исправления из раздела «Блокеры релиза».**

Ядро защиты сделано хорошо: подпись `initData` проверяется корректно, изоляция по `owner_id` последовательная, ключи BYOK зашифрованы AES-256-GCM и нигде не возвращаются, SSRF-защита пользовательского endpoint добротная (DNS-пиннинг, запрет приватных адресов и редиректов, лимиты времени и размера). Нет critical-находок и нет найденных способов прочитать или изменить данные другого пользователя.

Основные проблемы лежат не в классических уязвимостях, а в эксплуатации и приватности при открытой регистрации:

1. Один «сломанный» пользователь (например, заблокировавший бота) останавливает рассылку напоминаний и сводок всем остальным (S1).
2. Нет удаления данных, политики хранения и согласия, при том что хранятся данные о здоровье и финансах (S2).
3. Нигде нет ограничения частоты запросов и квот хранения, а регистрация открыта любому пользователю Telegram (S3).
4. Нет заголовков безопасности (S4).

`npm audit --omit=dev`: `found 0 vulnerabilities`. Все зависимости закреплены точными версиями (`save-exact=true` в `.npmrc`, в `package.json` нет `^` и `~`, `package-lock.json` присутствует). В git и его истории не найдено ни `.env*` (кроме `.env.example`), ни строк, похожих на токены Telegram, ключи Gemini, Groq, OpenRouter или строки подключения к БД с паролем.

## Проверено и безопасно

**1. Аутентификация и изоляция**
- `verifyTelegramInitData` (`src/server/telegram/auth.ts`): HMAC-SHA256 с ключом `HMAC("WebAppData", botToken)`, сравнение через `timingSafeEqual`, проверка формата хеша (64 hex), запрет дубликатов полей, валидация percent-кодирования, проверка `auth_date` (число, не в будущем, не старше 24 часов), `user.id` проверяется как положительное безопасное целое. Идентификатор берётся только из подписанного `user`, а не из `initDataUnsafe`. Параметр `ownerId` необязателен и не используется на маршрутах (многопользовательский режим).
- Изоляция: просмотрены все обращения к БД в `src/server/lifeos.ts` (около 150 запросов) и `src/server/telegram/bot.ts` (около 40): каждое чтение и запись по id содержит фильтр `ownerId`; для связанных таблиц (черновики по `captureDraftId`, позиции программы по `workoutDayId`, подходы) родительская строка предварительно проверена по владельцу. Дополнительно в схеме составные внешние ключи `(id, owner_id)` и `unique(id, owner_id)` на ключевых таблицах (`src/db/schema.ts`: `capture_drafts_id_owner_unique`, `finance_accounts_id_owner_currency_unique`, `workout_*_id_owner_unique` и другие) не дают связать строки разных владельцев на уровне БД.
- IDOR по uuid: команды `money.save/delete`, `food.save/delete`, `finance-plan.*`, `debt.*`, `recurring.*`, `exercise.*`, `day.*`, `draft.*`, `template.save`, действия кнопок бота (`all`, `none`, `cancel`, `edit`, `pay`, `template`, `tgt`), `/api/ai-providers` (`reorder`, `toggle`, `refresh`, `DELETE`) фильтруют по `ownerId` (`provider-accounts.ts:226-331`). Для `edit` обратный вызов устанавливает `editingCaptureId` без проверки владельца (`bot.ts:307-309`), но все дальнейшие чтения фильтруют по `ownerId`, а значение приходит из кнопки, созданной сервером (поддельный `callback_data` Telegram не пропустит); утечки нет.
- `isOwner(ctx)` в боте (`bot.ts:762`) дополнительно сверяет `ctx.from.id` с идентификатором владельца из контекста; обработка апдейта идёт под `withTelegramUser(owner.telegramUserId, ...)` по `owner_id` строки апдейта (`bot.ts:814`).
- Режим «наследного владельца» `requireConfiguredOwner` защищает метрики развёртывания; `/api/ai-quotas` отдаёт Gemini-метрики только ему (`src/app/api/ai-quotas/route.ts:16`).

**2. Webhook, cron, API**
- Webhook: секрет `X-Telegram-Bot-Api-Secret-Token` обязателен (без `TELEGRAM_WEBHOOK_SECRET` ответ 503), сравнение в постоянное время, лимит тела 256 КБ, проверка `update_id`, обработка только приватных чатов, сохранение апдейта до ответа и атомарный захват строки (`status in (received, failed)` в `UPDATE ... RETURNING`), уникальный индекс `telegram_updates_update_id_unique` обеспечивает идемпотентность; повторная доставка не обрабатывается дважды, `MAX_UPDATE_ATTEMPTS = 3` ограничивает повторы.
- Cron: требует `Authorization: Bearer <CRON_SECRET>`, сравнение в постоянное время, без секрета ответ 503; открытого доступа нет.
- Перечень маршрутов `src/app/api/*` (`ai-providers`, `ai-quotas`, `commands`, `cron`, `export`, `snapshot`, `telegram`): все, кроме `cron` и `telegram`, начинаются с `requireOwner`; `finance-plans-preview` — страница без обращений к БД (по каталогу; содержимое не разбиралось построчно). CORS не настроен, значит, кросс-доменные запросы с `Authorization` браузер не разрешит; куки не используются (авторизация только заголовком), CSRF неприменим. Ответы с данными имеют `Cache-Control: no-store`.
- Zod: все команды `commandSchema` ограничены по длине и диапазону (`text` 1-300, суммы до 1e12, подходы и повторы с верхними границами, `instructions` до 5000, UUID для идентификаторов); `/api/ai-providers` использует `strict()` и ограничивает число моделей (500), аккаунтов (20), позиций (0-19); часовой пояс проверяется через `Intl.DateTimeFormat` перед сохранением (`lifeos.ts:556`); дата снимка проверяется строго (`lifeos.ts:101`).

**3. Криптография BYOK**
- Алгоритм, длины IV и тега, проверка ключа (32 байта, канонический base64), случайный IV на каждое шифрование, отдельный класс ошибки без раскрытия данных (`provider-profiles.ts:150-186`). Открытый ключ не попадает в ответы API (`AiProviderAccountDto` содержит только `hasApiKey: true`), в логи (единственный `console.error` пишет только имя ошибки), в сообщения об ошибках (ошибки провайдеров сводятся к фиксированным текстам, тела ответов не показываются; `openai-compatible.ts`, `provider-catalog.ts`), в экспорт и резервные копии (таблицы ИИ не входят в `backupTables`), в снимок (`snapshot` не включает ИИ-таблицы). Ключ передаётся в заголовке (`authorization` или `x-goog-api-key`), не в URL. Управляющие символы в ключе отбрасываются (`openai-compatible.ts:48`), что исключает инъекцию заголовков.
- Ключи окружения для провайдеров в production не используются при передаче `selection` (см. S5 про fail-open).

**4. SSRF и пользовательский endpoint** (`src/server/ai/safe-fetch.ts`)
- Только `https:`, запрет учётных данных, `?`, `#`, `%` в имени хоста, обхода пути (`..`, `%2e`), `localhost`, `.local`, `.internal`, `.test` и подобных суффиксов, имён без точки. Все DNS-ответы (`all: true`) проверяются на публичность: IPv4 (loopback, RFC1918, CGNAT, link-local, документационные, multicast, зарезервированные), IPv6 (только `2000::/3`, исключая документационные, ORCHID, 6to4, IPv4-mapped с проверкой по IPv4-правилам), нестандартные формы IPv4 нормализуются парсером `URL`.
- DNS rebinding закрыт: проверенные адреса подставляются в `lookup` исходящего `https.request`, повторного разрешения имени нет. Редиректы (3xx) отвергаются. Ограничения: таймаут сокета и общий таймаут (по умолчанию 18 с, максимум 60 с), лимит ответа 256 КБ (до 1 МБ), `accept-encoding: identity` (нет декомпрессионных бомб), лимит тела запроса 12 МБ. Проверка повторяется при каждом запросе, а не только при сохранении.
- Остальные провайдеры (Gemini, Groq, OpenRouter) используют фиксированные хосты; идентификатор модели в URL Gemini проходит `encodeURIComponent`.

**5. Инъекции**
- SQL: пользовательский ввод во все `sql\`\`` попадает как параметр (`bot.ts:281,286,803,841`; `backup.ts` использует `sql.identifier` для имён таблиц и колонок из схемы, а не из ввода). Конкатенации SQL-строк нет.
- Telegram: `parse_mode: "HTML"` применяется только к фиксированным текстам меню (`bot.ts:68,76,89,101`); тексты с пользовательскими данными (черновики, напоминания, сводки) отправляются обычным текстом, поэтому HTML-инъекция через названия еды, имена должников или категории невозможна. Callback-данные разбираются строго (`split(":")`, числа проверяются, идентификаторы фильтруются по владельцу).
- XSS в Mini App: React экранирует вывод, небезопасных API нет (см. S4).
- Prompt injection: пользовательские данные передаются как JSON внутри явной пометки «данные, а не инструкции»; ответ модели проходит `strict()`-схему с лимитами; ИИ не вызывает инструментов и не пишет в БД напрямую, только создаёт черновики (`lifeos.ts:525-540`), записать их может только пользователь. Фото ограничено 8 МБ и типами jpeg/png/webp (проверка base64 и размера в `analyze.ts:453-461`, `openai-compatible.ts:200-210`).

**6. Прочее**
- Загрузка фото из Telegram: потоковое чтение с обрывом при превышении 8 МБ, таймаут, URL строится из `file_path` Telegram (`bot.ts:605-640`); токен бота присутствует только в URL запроса к `api.telegram.org`, в логи не попадает.
- Секреты в клиентском бандле: переменные `NEXT_PUBLIC_*` — только `NEXT_PUBLIC_APP_VERSION` и `NEXT_PUBLIC_RELEASE_HISTORY` (`next.config.ts:21-24`). Страница `src/app/page.tsx` передаёт клиенту только булево «настроено».
- `poweredByHeader: false` отключает заголовок `X-Powered-By`.
- Резервное копирование: выборка по владельцу, лимиты 100 000 строк и 25 МБ, восстановление только в пустую БД, валидация формата (`validateBackup`).

**Не проверено**: параметры Vercel (защита веток, переменные окружения, заголовок HSTS, лимиты тела и Firewall), настройки Neon (разрешённые IP, шифрование и срок хранения резервных копий и точек восстановления PITR), настройки cron-job.org, фактические значения секретов, поведение каскадного удаления с `restrict` (S2), поведение в клиентах Telegram, политики обучения на данных у провайдеров ИИ (S2), содержимое архива `Здоровье и спорт.zip`.

## Блокеры релиза

Обязательно исправить перед публичным запуском:

1. **S2: удаление данных, политика конфиденциальности, согласие и сроки хранения.** Без этого публичный сервис с данными о здоровье не готов юридически (получить подтверждение юриста относительно применимого регулирования; в отчёте юридической оценки нет).
2. **S1: изоляция сбоев в cron.** Иначе после запуска первый же пользователь, заблокировавший бота, остановит напоминания остальным.
3. **S3: ограничение частоты и квот** (минимум: лимит апдейтов, экспортов и подключений ИИ на пользователя; решение об открытой регистрации против списка разрешённых на этапе беты).
4. **S12: проверить, что `CRON_SECRET` и `TELEGRAM_WEBHOOK_SECRET` случайные и длиной не менее 32 символов** (значения не читались).

Желательно до запуска: S4 (заголовки, начать с Report-Only), S5 (fail-closed), S6, S7. Остальное можно планировать после запуска.

## Рекомендации по эксплуатации

- Секреты: хранить только в переменных окружения Vercel (Production/Preview раздельно), ротация при подозрении на утечку. Порядок ротации `TELEGRAM_BOT_TOKEN`: новый токен, `npm run telegram:register`, перевыпуск `TELEGRAM_WEBHOOK_SECRET`. Порядок ротации `AI_PROVIDER_ENCRYPTION_KEY` пока невозможен без потери ключей пользователей (S8): до реализации формата `v2` не менять ключ и хранить его копию отдельно (менеджер паролей).
- Preview-развёртывания не должны использовать production `DATABASE_URL` и production-секреты (проверить в Vercel).
- Neon: включить защиту от случайного удаления, проверить срок точек восстановления и снимков, настроить отдельную роль БД приложения с правами только на нужные таблицы (миграции выполнять отдельной ролью); учесть, что бесплатные квоты исчерпываются раньше при открытой регистрации (S3).
- Мониторинг: уведомление о ненулевой доле ответов 5xx на `/api/cron` и `/api/telegram`, размер таблицы `telegram_updates`, число строк в `owner_settings`, использование квот Neon.
- Cron-job.org: проверять, что задание получает 200; при 503 (S1) срабатывает тревога, а не молчание. Расписание вызова не чаще чем нужно для времени сводок.
- Резервные копии: делать `npm run backup:export` из доверенной среды, шифровать (`age`/`gpg`), хранить отдельно от БД, периодически проверять восстановление в пустой БД (S9). Помнить, что копия охватывает данные только одного владельца (`TELEGRAM_OWNER_ID`), то есть это не резервная копия всей базы: для полной копии нужны снимки Neon.
- Реагирование на инцидент: при подозрении на утечку токена бота сразу отозвать токен в BotFather и перерегистрировать webhook; при подозрении на утечку ключа шифрования уведомить пользователей и попросить перевыпустить ключи провайдеров (старые считать скомпрометированными).
- Зависимости: `npm audit --omit=dev` перед каждым релизом (на 2026-11-15 уязвимостей нет); версии закреплены, обновления делать через PR с прогоном `npm test`, `npm run typecheck`, `npm run lint`.
- В публичных описаниях честно указывать границы: обработка в рамках `after()` не является долговечной очередью (CLAUDE.md), а интеграции Telegram, BYOK, cron-job.org и Telegram WebView ещё требуют сквозной проверки.
