# Эксплуатация (runbook)

Практические процедуры для владельца развёртывания. Всё ниже составлено по коду версии 0.25.0; шаги, которые ни разу не выполнялись на production, помечены «не проверено». Что подтверждено на реальных сервисах, описано в [статусе](status.md). Развёртывание с нуля — [deployment.md](deployment.md), переменные — [configuration.md](configuration.md), схема БД — [database.md](database.md).

## Быстрая диагностика

| Симптом | Где смотреть | Что означает |
|---|---|---|
| Приложение не отвечает | `GET /api/health` | Ответ `{"status":"ok","version":"..."}` подтверждает только, что процесс запущен. К базе маршрут не обращается |
| Mini App показывает заглушку | Переменные `DATABASE_URL`, `TELEGRAM_BOT_TOKEN` на Vercel | Главная страница считает приложение «не настроенным», если одной из них нет |
| API отвечают 401 | Подпись Telegram `initData` недействительна или старше 24 часов | Пользователю нужно открыть Mini App заново из бота |
| API отвечают 429 | Сработал rate limit | См. раздел ниже |
| Бот молчит | `getWebhookInfo`, таблица `telegram_updates`, логи Vercel | См. «Зависшие Telegram updates» |
| Сводки не приходят | Журнал cron-job.org, ответ `/api/cron`, настройки пользователя | См. «Cron» |

## Логи Vercel

Логи функций доступны в Vercel (Project, Logs). Сообщения кода не содержат персональных данных и секретов; полезные строки для поиска:

- `LifeOS telegram update failed` — обработка update завершилась ошибкой (с `updateRowId`, номером попытки и именем ошибки).
- `LifeOS cron: owner failed` — для одного пользователя не выполнились плановые задачи (остальные пользователи продолжают обрабатываться).
- `LifeOS cron: rate limit cleanup failed` — не удалось очистить старые счётчики rate limit.
- `LifeOS rate limit unavailable, allowing request` — таблица счётчиков недоступна или ошибка БД; лимитер пропускает запрос.
- `LifeOS telegram rate limit exceeded` — сообщения пользователя отброшены лимитом.
- `LifeOS request failed` — необработанная ошибка в API (только имя ошибки).
- `LifeOS security: ... короче 32 символов` — слабый `CRON_SECRET` или `TELEGRAM_WEBHOOK_SECRET`.

Мониторинга, алертов и сторонних сервисов ошибок в проекте нет: проверка выполняется вручную по логам и журналу cron-job.org.

## Cron и плановые задачи

`/api/cron` вызывает внешний планировщик (cron-job.org) с `Authorization: Bearer <CRON_SECRET>`. За один вызов маршрут:

1. Повторяет Telegram updates (см. ниже).
2. Удаляет счётчики rate limit старше двух суток.
3. Для каждого пользователя по порядку создания профиля: напоминания о платежах и долгах, ежедневная сводка, недельная сводка (воскресенье), напоминание взвеситься (четверг). Включённые функции и время берутся из настроек пользователя; `DAILY_SUMMARY_TIME`/`WEEKLY_SUMMARY_TIME` — значения по умолчанию.

Ответ: `{"ok":true,"sent":N,"failed":0}`. Если у части пользователей задачи упали, ответ `{"ok":false,...,"failed":K}` при статусе 200, а подробности (`ownerId`, имя ошибки) только в логах. Время выполнения функции ограничено 60 секундами (`maxDuration`); при большом числе пользователей прогон может не успеть, это не проверялось. Дедупликация уведомлений основана на таблице `notification_deliveries`.

Если cron-job.org не вызывает маршрут, сводки, напоминания и повтор зависших updates не выполняются совсем.

## Зависшие и неудачные Telegram updates

Webhook (`/api/telegram`) сохраняет update в `telegram_updates` до ответа Telegram, затем обрабатывает его через `after()`. Статусы: `received`, `processing`, `processed`, `failed`. После успешной обработки `payload` очищается (`{}`).

- Update в статусе `processing` дольше 120 секунд cron переводит в `failed` с `last_error = 'processing_timeout'`.
- Cron повторяет `received` и `failed` updates, у которых попыток меньше 3 (`MAX_UPDATE_ATTEMPTS`), не более 5 за вызов.
- После трёх неудач update остаётся в `failed` вместе со своим `payload` (исходное сообщение пользователя); повторно сам он не обрабатывается. Автоматической очистки таких строк в коде нет.
- Повторная доставка Telegram того же `update_id` для `failed` сбрасывает строку в `received` и запускает обработку заново.

Диагностика (в SQL-консоли Neon или `psql`; запросы читают служебные данные, содержимое сообщений не выводите в чаты и тикеты):

```sql
SELECT status, count(*) FROM telegram_updates GROUP BY status;
SELECT id, status, attempt_count, last_error, received_at
  FROM telegram_updates WHERE status IN ('received','processing','failed')
  ORDER BY received_at DESC LIMIT 50;
```

Принудительный повтор вручную (не проверено на production): обнулить счётчик попыток у конкретной строки и дождаться следующего вызова cron.

```sql
UPDATE telegram_updates SET status = 'failed', attempt_count = 0 WHERE id = '<uuid>';
```

Состояние самого webhook: метод Bot API `getWebhookInfo` (`pending_update_count`, `last_error_message`). Перерегистрация: `npm run telegram:register`.

## Rate limit

Счётчики хранятся в таблице `rate_limit_counters` (ключ `bucket:subject`, фиксированное окно), без Redis. Пороги — в `src/server/rate-limit.ts`, объект `RATE_LIMITS`:

| Корзина | Предел | Окно | Субъект |
|---|---|---|---|
| `commands` | 120 | 60 с | пользователь |
| `snapshot` | 120 | 60 с | пользователь |
| `ai-providers` | 30 | 60 с | пользователь |
| `ai-quotas` | 30 | 60 с | пользователь |
| `export` | 5 | 3600 с | пользователь |
| `telegram-messages` | 60 | 60 с | пользователь Telegram |
| `new-profiles` | 60 | 3600 с | все пользователи вместе |

Чтобы изменить порог, поправьте `limit` или `windowSeconds` в `RATE_LIMITS`, выпустите изменение обычным порядком (ветка, PR, версия и запись в CHANGELOG) и задеплойте; отдельной настройки в окружении нет. Поведение: API отвечает 429 с заголовком `Retry-After`; сообщения боту сверх лимита молча отбрасываются с подтверждением Telegram; `new-profiles` блокирует создание новых профилей. Если база недоступна, лимитер пропускает запрос (fail open) и пишет в лог. Состояние счётчиков:

```sql
SELECT key, window_start, count FROM rate_limit_counters ORDER BY window_start DESC, count DESC LIMIT 50;
```

Сбросить лимит конкретному субъекту можно удалением его строк в `rate_limit_counters`.

## Резервное копирование и восстановление

Три слоя; ни один не проверен восстановлением на production.

1. Neon: ветки и point-in-time restore (зависят от тарифа Neon, проверьте доступное окно). Это единственный способ вернуть все данные всех пользователей, включая зашифрованные ключи ИИ.
2. Экспорт владельца скриптом `scripts/backup.ts`:

   ```bash
   npm run backup:export -- ./lifeos-backup.json
   npm run backup:restore -- ./lifeos-backup.json
   ```

   Нужны `DATABASE_URL` и `TELEGRAM_OWNER_ID`: копия строится только для профиля владельца (по Telegram ID). Файл создаётся без перезаписи существующего с правами `0600`, но не шифруется: храните его как персональные данные. Пределы: 25 МБ и 100 000 строк. В копию входят данные модулей (питание, финансы, зал, профиль); не входят ключи ИИ, `telegram_updates`, `notification_deliveries`, `rate_limit_counters` — после восстановления ключи ИИ нужно подключить заново. Восстановление выполняется одной транзакцией и принимает копию только для совпадающего `TELEGRAM_OWNER_ID` и пустого профиля; для остальных пользователей этот путь недоступен.
3. Экспорт пользователя: `GET /api/export` (не чаще 5 раз в час) и кнопка в настройках Mini App (см. [privacy-policy.md](privacy-policy.md)).

Рекомендуется перед каждой миграцией production создавать ветку или точку восстановления Neon.

### Проверка восстановления (учения, делает владелец)

Цель: убедиться, что данные возвращаются из Neon, и записать фактическое окно восстановления. Production при этом не меняется.

1. Neon Console → проект → Branches → Create branch. Источник: `main`, момент времени: например, час назад (Time). Дождитесь статуса Ready.
2. Скопируйте connection string новой ветки и подставьте во временный `DATABASE_URL` (только в локальную оболочку, не в Vercel и не в файлы репозитория).
3. Сравните с production: число строк в основных таблицах (`finance_entries`, `nutrition_entries`, `weight_entries`, `workout_sessions`) и последнюю применённую миграцию в `drizzle.__drizzle_migrations`. Расхождение допустимо только на записи, сделанные после выбранного момента.
4. Запустите приложение локально с этим `DATABASE_URL` и откройте Mini App под тестовым профилем: данные должны читаться.
5. Удалите ветку в Neon и очистите переменную окружения.
6. Запишите в [status.md](status.md): дату учений, тариф Neon, фактическое окно восстановления и результат шагов 3–4.

Если шаги 3–4 не прошли, это блокер RC (B10): не выпускайте релиз-кандидат, пока восстановление не подтверждено.

### Восстановление production после потери или порчи данных

1. Остановите дальнейшую порчу: поставьте на паузу cron-job.org и, если причина в коде, откатите деплой (см. [deployment.md](deployment.md)).
2. Создайте ветку Neon на момент до порчи (как в учениях, шаги 1–3) и убедитесь, что данные в ней целы.
3. В Neon сделайте Restore: либо переключите production на восстановленную ветку (новый connection string в `DATABASE_URL` на Vercel и повторный деплой), либо выполните Restore на месте. Выбор зависит от тарифа; текущую ветку перед этим сохраните копией.
4. Проверьте `/api/health` и вход в Mini App, затем включите cron и проверьте, что зависшие updates повторяются (раздел «Зависшие и неудачные Telegram updates»).
5. Сообщите пользователям, за какой период данные могли потеряться (записи между точкой восстановления и инцидентом).
6. Запишите инцидент и причину в журнал эксплуатации.

### Откат миграции

Миграции Drizzle только вперёд, автоматического отката нет. Порядок:

1. До миграции создайте ветку Neon (точка отката). Ветка хранится, пока не удалена.
2. Если миграция сломала приложение, а новых пользовательских данных ещё нет, откатите код (revert merge commit в `main`, Vercel задеплоит предыдущее состояние) и восстановите базу из ветки шага 1.
3. Если пользователи уже писали данные в новую схему, откат из ветки их потеряет. Тогда пишите обратную миграцию вручную (новый файл миграции, который возвращает схему), проверяйте её на ветке Neon и применяйте обычным путём.
4. Запись в `drizzle.__drizzle_migrations` руками не правьте: она связана с хэшем файла миграции.

## Ротация и потеря `AI_PROVIDER_ENCRYPTION_KEY`

Ротации ключа в коде нет. Ключи ИИ пользователей хранятся как `v1:<iv>:<tag>:<ciphertext>` (AES-256-GCM); идентификатора версии ключа шифрования в записи нет, поэтому одновременно работает только один ключ. Следствия:

- Потеря или замена значения в окружении делает все сохранённые ключи ИИ нечитаемыми. Приложение при этом не теряет остальные данные, но разбор через ИИ перестаёт работать, пока пользователи не введут ключи заново (точное поведение интерфейса в этом случае не проверялось).
- Плановая замена ключа потребует отдельной процедуры перешифровки: прочитать `encrypted_api_key` в `ai_provider_accounts` и `ai_provider_profiles`, расшифровать старым ключом, зашифровать новым и записать назад одной транзакцией, затем сменить переменную в Vercel. Такого скрипта нет; его нужно написать и проверить на ветке Neon до применения.
- Компрометация ключа: сгенерируйте новый (`openssl rand -base64 32`), задайте его в Vercel и попросите пользователей заново ввести ключи ИИ (старые зашифрованные значения очистите), а сами API-ключи у провайдеров отзовите и выпустите новые.

Дополнительная привязка шифрования (AAD) и ротация перечислены в [плане релиза](release-plan.md) как работа после RC.

## Смена других секретов

- `TELEGRAM_WEBHOOK_SECRET`: обновите переменную в Vercel, задеплойте и выполните `npm run telegram:register`; до перерегистрации Telegram будет получать 401.
- `CRON_SECRET`: обновите переменную в Vercel и заголовок задания в cron-job.org одновременно.
- `TELEGRAM_BOT_TOKEN`: после перевыпуска токена в BotFather обновите переменную и перерегистрируйте webhook.

## Пользователь заблокировал бота

Специальной обработки блокировки бота в коде нет. Отправка уведомления такому пользователю завершается ошибкой; плановые задачи ловят её по каждому пользователю (в логе `LifeOS cron: owner failed`), остальные пользователи не страдают, но ответ cron содержит `ok:false` и `failed > 0` при каждом прогоне. Повторяются ли попытки отправки в следующих вызовах и сколько раз, дедупликацией не проверялось. Варианты (не проверены):

- Отключить сводки пользователю в базе (платёжные и долговые напоминания управляются функциями модулей отдельно):

  ```sql
  UPDATE owner_settings SET daily_summary_enabled = false, weekly_summary_enabled = false, weight_reminder_enabled = false
  WHERE telegram_user_id = '<telegram id>';
  ```

- Удалить данные пользователя по его запросу (после выхода функции удаления из ветки `feat/data-rights-0-25` — через неё; до того — удалением строки в `owner_settings`, что каскадно удаляет связанные данные). Удаление необратимо: сначала убедитесь в личности и создайте точку восстановления.

## Данные пользователей

Запросы пользователей на экспорт и удаление выполняются через Mini App (настройки); процесс и сроки описаны в [privacy-policy.md](privacy-policy.md). Не просматривайте и не копируйте содержимое пользовательских данных без необходимости: профили содержат здоровье, финансы и ключи ИИ.
